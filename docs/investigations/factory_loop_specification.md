# Factory Loop Specification (CC-1 directive, Track B)

**Status: specification only. No code changed to produce this document.**
**Standard: 100% accuracy — every claim below is either a direct code/data citation or explicitly marked as a design recommendation.**

Target loop shape, as given in the directive:

```
Adam/Eve -> Test harness -> PROMISING/borderline: Trial (forward-testing)
                          -> DIED: Graveyard (distilled, not raw)
Graveyard -> Repair workbench -> repaired & passes: back into Trial
                               -> still fails: stays in Graveyard
Graveyard grows over time -> read fresh by every Adam/Eve session -> next generation -> repeat
```

## 0. Current-state ground truth (read before anything else below)

Before designing the loop, four load-bearing facts, all confirmed directly from code and committed data as of 2026-08-04:

**0a. Zero hypotheses have ever reached SURVIVED or PROMISING-WATCHLIST.** `docs/site_data/agent_performance.json`'s cumulative totals across all 4 committed Adam runs: `survived=0, promising_watchlist=0, tested=0`. `docs/site_data/eve_hypotheses.json` (16 records across all Eve sessions to date): 5 `DIED`, 1 `SKIPPED` (TOO_SLOW), 10 with no verdict (UNTESTABLE_BY_DSL / refused-data records from Sessions 0 and 0-B). **Not one SURVIVED or PROMISING-WATCHLIST record exists anywhere in this repository.** Every design below is for a Test→Trial door that has never yet had anything walk through it. This changes the priority calculus: correctness and auditability of the admission path matter far more right now than throughput, since there is no backlog to clear.

**0b. A "Repair Lab v1" already exists, fully built and tested, and is entirely un-wired.** `nero_core/research_agent/repair_lab.py` (861 lines) + `repair_forward_tracker.py` + `repair_historical_reservation.py` implement exactly the "Graveyard -> Repair workbench -> back into Trial or stays in Graveyard" half of the target loop — eligibility gating (DIED only), an LLM diagnosis-and-one-modification step with a hard 4-type boundary (`entry_threshold`, `exit_structure`, `direction_add_mirror`, `asset_timeframe_change`), in-chain duplicate rejection, a 4-attempt cap counted at launch not resolution, two independent "genuinely fresh data" mechanisms (historical reservation and forward-tracking, reusing `live_scheduler`'s own proven single-tick pattern against a dedicated SQLite file), and an append-only replay-based chain-state record. It has 8 dedicated test files. **Nothing calls it.** `test_repair_lab_no_auto_wire.py` exists specifically to guarantee this stays true — it is a standalone, human-invoked tool, not a pipeline stage. B3 below addresses whether/how to wire it in, not whether to build it (already built).

**0c. `docs/site_data/graveyard.json` and `docs/site_data/failure_patterns.json` are two different, both entirely hand-curated files.** `graveyard.json` (21 entries: `name`, `family`, `what_was_tested`, `why_it_died`, `source_doc`) is read by nothing in `nero_core/` or `tools/` (only referenced by one test). `failure_patterns.json` (13 entries: `name`, `family`, `failure_pattern`, `fixable`, `source_doc`) is the file Adam (`hypothesis_gen.py`, `pipeline.py`) and Eve (`context.py`, `session.py`, `llm_client.py`) actually read as graveyard context. **No code anywhere writes either file.** A human writes a markdown investigation report, then hand-authors a distilled JSON entry. This is the entire current "distillation" mechanism: 100% manual, zero automation, and the two files have silently diverged: verified by exact name comparison, `graveyard.json`'s 21 entries and `failure_patterns.json`'s 13 are NOT a subset relationship either direction — `RANGE_MEAN_REVERSION` exists in `failure_patterns.json` (the file Adam/Eve actually read) but nowhere in `graveyard.json`, while 9 entries (including `REGIME_TRANSITION`, all 4 `MACRO_RISK_ON` extensions, and `RANGE_MATURITY gate`) exist in `graveyard.json` but were never distilled into `failure_patterns.json` at all — meaning Adam and Eve have never been told about those 9 killed mechanisms.

**0d. `apply_fdr_correction` runs PER-SESSION today, on that session's own hypotheses only.** `nero_core/eve/pipeline.py:267-275`: `scored = scoring.score_all(result.hypothesis_records, ...)` — `result.hypothesis_records` is the current session's own turn loop output, nothing else. `apply_fdr_correction(scored, field=...)` is called on that same per-session list. Confirmed directly: Session 1's FDR family was its own 6 hypotheses (2 excluded as self-derivative, so an effective family of 4), not a family spanning any other session. This is direct evidence for B4.

## B1. Test→Trial entry

**Finding:** There is no "Trial" concept anywhere in this codebase today. A SURVIVED/PROMISING-WATCHLIST verdict currently means exactly one thing: `auto_tester.py:685` sets `review_status = REVIEW_PENDING` ("pending_human_approval") on the `TestResult`, which is written to `agent_test_results.json` (Adam, never committed by the workflow) or folded into the scored record in `eve_hypotheses.json` (Eve, committed). Nothing forward-tracks it, nothing schedules it for anything, and nothing distinguishes "reviewed and approved" from "never looked at" beyond that one string field. The only REAL forward-testing infrastructure in this codebase is `repair_forward_tracker.py` — but it is scoped exclusively to Repair Lab attempts (its own SQLite file, `data/repair_lab_forward_tracking.db`, its own `REPAIR_LAB_ATTEMPT:` strategy-name prefix in `truth_ledger.execution_log`), not available to a fresh (non-repaired) SURVIVED hypothesis today.

**Confidence:** confirmed-from-code (0a, 0b above) and confirmed-from-data (agent_performance.json cumulative, eve_hypotheses.json verdict counts).

**Data-shape recommendation:** A Trial entry should be a thin wrapper, not a new hypothesis representation — reuse `repair_forward_tracker.py`'s already-proven `ForwardTickResult`/execution-log-row shape (it already solves "track open/closed paper trades against a hypothesis with no historical replay, using the exact tested `live_scheduler` single-tick pattern") rather than inventing a second forward-tracking mechanism. Concretely: `{trial_id, source_hypothesis_ref: {origin: "adam"|"eve", hypothesis_name, session_id_or_run_ref}, entry_verdict: {verdict, p_value_oos, review_status}, opened_at, status: OPEN|SURVIVED_TRIAL|FAILED_TRIAL, forward_tracking_db_ref}`.

**Attribution/traceability recommendation:** This is a real, present gap, not a hypothetical one. Adam's own hypothesis records (`agent_hypotheses.json`) carry `generated_at` and `discovery_channel` but **no run identifier at all** — confirmed by listing every field on a real record: `hypothesis_name, mechanism, entry_rule, structured_entry_rule, exit_rule, stop_rule, structured_exit_plan, asset, timeframe, differs_from_graveyard, expected_frequency_claim, generated_at, cost_usd, source, discovery_channel, source_url, source_description, source_tier, paraphrase_confirmed, graveyard_check` — none of these is a back-reference to a specific `pipeline.run_pipeline()` invocation. Eve's records DO carry `session_id` already (confirmed on every `eve_hypotheses.json` record). **Recommendation: before building Test→Trial, add a `run_id` field to Adam's hypothesis records** (a UUID minted once per `run_pipeline()` call, analogous to Eve's `session_id`) — otherwise a Trial entry sourced from Adam can never be traced back to which run produced it, the same class of gap A1's own run-summary-persistence fix (item 53) closed for run-level aggregates but not per-hypothesis records.

**Volume estimate:** **Zero**, across every session/run committed to date (0a). State this explicitly rather than sizing the admission path for a backlog that does not exist.

## B2. Test→Graveyard with distillation

**Finding:** The "distillation" the directive asks about already has a real, working FORMAT (`failure_patterns.json`'s 5-field shape: `name, family, failure_pattern, fixable, source_doc`) but zero automation producing it (0c). Today, a DIED hypothesis becomes a graveyard entry only if a human notices it, writes an investigation markdown doc, and hand-types a JSON entry to match. There is no code path from `agent_test_results.json`'s per-hypothesis DIED record (or Eve's `verdict_combined: "DIED"` record) to either graveyard file.

**Confidence:** confirmed-from-code (repo-wide grep for both filenames found zero writers outside tests).

**Concrete distillation approaches, with tradeoffs:**

1. **LLM-summarized, human-approved (closest to the current process, minimal new trust surface).** After N DIED verdicts accumulate for a `(mechanism family)` (grouped by shared entry-rule shape, not by literal hypothesis name — see graveyard's own `family` field, e.g. "Fair Value Gap" spans multiple named variants), an LLM call (reusing `hypothesis_gen`'s own `_call_claude`/cost-accounting pattern, not a new one) proposes a `failure_patterns.json`-shaped entry from the aggregate stats (same "diagnosis sees aggregate stats, never raw data it wasn't shown" discipline `repair_lab.py`'s own diagnosis step already enforces). The entry sits in a `review_status: pending` state until a human approves it — mirroring `auto_tester.py`'s own existing `REVIEW_PENDING` convention rather than inventing a new one. *Tradeoff:* still requires a human in the loop, so it does not remove the current bottleneck, only shrinks the manual-writing effort. This is the safest choice given 0a (there is no volume pressure yet forcing faster throughput) and this project's own explicit non-negotiable ("no strategy may silently self-modify" — a graveyard entry silently authored end-to-end by an LLM and never reviewed is the same category of risk).
2. **Rule-based aggregation, zero LLM.** A deterministic script groups DIED records by `(mechanism_family, asset_class)`, computes `why_it_died` from a fixed template (e.g. "N/M configs DIED; median OOS p-value X; Y% failed on sample-thinness per `is_sample_thin`"). *Tradeoff:* cheap and fully auditable (no LLM cost, no LLM error mode), but produces mechanical, low-texture entries — loses the qualitative diagnosis that makes `failure_patterns.json`'s real entries useful context for a future Eve session (e.g. FVG_REVERSION's actual entry: "the gap-touch trigger itself wasn't adding meaningful value beyond randomly-timed entries in the same trend regime" — a template cannot produce that sentence, only an LLM reading the real numbers can).
3. **Full automation, no human gate.** LLM-summarized entries write directly to `failure_patterns.json`, no review step. *Tradeoff:* fastest, but this is the option this project's own stated design philosophy already argues against — `repair_lab.py`'s SURVIVED/PROMISING-WATCHLIST outcomes explicitly still route through human review "regardless of how many attempts succeed" (module docstring); a DIED-side automation that skips review while the SURVIVED-side doesn't is an inconsistent bar. Not recommended.

**Recommendation:** Option 1, reusing `REVIEW_PENDING`/human-approval as the gate, triggered per mechanism-family once its DIED count crosses a threshold (propose 3, matching this project's own `MIN_SAMPLE_SIZE`-adjacent "don't generalize from one data point" instinct visible everywhere else in this codebase — not a hard recommendation, a starting number for the human running the loop to adjust). **Also recommend reconciling `graveyard.json` and `failure_patterns.json` into one file before adding automation to either** — building an automated writer for one while the other silently drifts further out of sync compounds the existing gap rather than fixing it.

## B3. Repair→Trial

**Finding:** Repair Lab v1's own two "genuinely fresh data" mechanisms — `repair_historical_reservation.py` (reserves an unused historical segment) and `repair_forward_tracker.py` (the `live_scheduler`-pattern single-tick forward tracker) — are **already a complete, working admission-to-forward-testing path**, purpose-built for exactly the "repaired & passes -> back into Trial" arrow. They do NOT reuse Adam/Eve's own hypothesis-generation admission mechanism (there isn't one to reuse yet, per B1) and structurally could not: a repair attempt is not a fresh hypothesis, it is one link in an explicitly-lineaged chain (`reconstruct_chain_state`'s own docstring: "there is no way to read this chain's own attempt 3 without also seeing attempts 1-2 and their own outcomes right next to it").

**Confidence:** confirmed-from-code.

**Recommendation:** Repair→Trial needs its OWN admission path, not B1's — but the two paths should converge on the same downstream `Trial` record shape (B1's recommended shape above), with the `source_hypothesis_ref` field distinguishing `origin: "fresh"` (Adam/Eve direct) from `origin: "repaired", repair_chain_id: ..., attempt_id: ...`. This gets full lineage for free (a repaired hypothesis in Trial can always be traced back through `reconstruct_chain_state` to its original DIED ancestor) without forcing repair attempts through machinery built for a different admission shape (fresh hypotheses don't have a 4-attempt cap or an in-chain-duplicate check; repair attempts do, and reusing B1's mechanism wholesale would either lose that enforcement or require bolting it on awkwardly).

## B4. Multiplicity/FDR at factory scale

**Finding:** As established in 0d, `apply_fdr_correction` is currently a **per-session** correction — confirmed directly from the call site, not inferred. The pre-registration document (`eve_session_registry.json`) states the kill criterion as *"5% OOS survival, FDR-corrected, across the full cross-asset family"* — this phrase is genuinely ambiguous between "each session's own family, corrected independently" (what the code does today) and "one family spanning all 8 sessions' hypotheses together" (what "across the full cross-asset family" more naturally reads as, and what a statistician would expect from an 8-session pre-registered campaign designed to answer one aggregate question).

**Confidence:** confirmed-from-code (the per-session mechanism) / unable-to-verify (which reading the pre-registration document's authors intended — the phrase itself is the only evidence, and it supports both readings).

**Honest assessment, as explicitly requested (not just a patch):** The per-session correction, as currently implemented, is defensible ONLY as long as "8 sessions" stays a fixed, small, pre-committed number decided in advance — which is exactly the current design (0d, `eve_session_registry.json`'s own `next_countable_session_number` tracking). The moment a continuous Factory Loop exists — sessions run indefinitely, Trial/Repair feed back into future sessions' own context, the campaign has no natural end — **per-session correction stops being defensible on its own terms**, for a reason distinct from the ambiguity above: Benjamini-Hochberg's guarantee is a property of the WHOLE family tested, and a family redefined fresh every session, forever, means the "5% false-discovery rate" is only ever asserted about one session's tiny handful of hypotheses at a time (Session 1's real family size was 4, post-self-derivative-exclusion) — never about the true cumulative multiple-testing burden of running the loop indefinitely. An analyst reading "Eve cleared 5% FDR-corrected significance" after 50 continuous-loop sessions would reasonably assume that 5% bound holds across all ~200+ hypotheses tested, when the code as it stands today would only ever have asserted it 4-6 hypotheses at a time, 50 separate times — a materially weaker and different statistical claim. **This is not a knob to retune; it requires an explicit design decision before a continuous loop launches:** either (a) redefine "family" as a rolling window (e.g. every hypothesis tested in the trailing N sessions, re-corrected together each time a new session's results land — statistically sound but means an individual hypothesis's own FDR-survival status can flip as new sessions arrive, which needs its own honest UI/reporting treatment so a survived-then-later-flipped hypothesis is never silently re-labeled), or (b) keep per-session correction but explicitly reframe the reported claim as "N independent per-session tests at 5% FDR each," dropping "across the full cross-asset family" language entirely since it would no longer be true. **Recommendation: (a), because it is the interpretation that matches the pre-registration document's own stated words** — but this is a statistical-design call for a human to make explicitly, not something to silently pick.

## B5. Self-contamination/provenance

**Finding:** The contamination-tagging mechanism already in production (`nero_core/eve/scoring.py`) supports exactly 3 tag names today: `DERIVATIVE` (near-repeat of an Adam-history hypothesis), `SELF_DERIVATIVE` (near-repeat of Eve's own prior-session history), and `LOOKAHEAD_RISK` (session-level, kept in a separate `lookahead_risk_flags` list rather than per-hypothesis `contamination_tags` — confirmed: `tag_lookahead_risk`'s return value is stored via `_persist_session_record_amendments`, not merged into any hypothesis's own `contamination_tags`). Every tag currently added is "measure, never gate" by explicit design (module docstring, restated at every tagging site) — this discipline should extend to whatever provenance tags the Factory Loop adds, not be relaxed for them.

**Confidence:** confirmed-from-code.

**Provenance tag design recommendation:** Two new fields, not folded into `contamination_tags` (which is reserved for "similarity to a specific prior hypothesis," a different kind of fact than "who/what produced this"):
- `origin_agent: "adam" | "eve"` on every hypothesis record, set once at generation time (trivial to add — Adam and Eve already write structurally distinct records, this just makes the distinction explicit and machine-queryable rather than inferable from which file the record lives in).
- `origin_chain: null | {repair_chain_id, attempt_id}` (B3's own field, generalized here) so a Graveyard/Trial record's full lineage is queryable without cross-referencing multiple files by hypothesis name string-matching (this project's own `check_duplicate`/`check_graveyard_match` functions already rely on name/description matching as a KNOWN, documented limitation — provenance tracking should not add a second place with the same weakness).

**Graveyard-contamination interaction:** With `origin_agent` in place, a graveyard-distillation entry (B2) can honestly report "died 4 times under Adam, 1 time under Eve" instead of an anonymous count — directly useful for a future session's own context (an LLM reading "Eve has independently rediscovered and killed this mechanism twice" is a stronger signal than an undifferentiated "died 6 times"). This also lets a future audit answer "is Eve mostly rediscovering Adam's own graveyard, or finding genuinely new failure modes" — a real open question this project has not yet been able to answer from data, since no provenance field exists to answer it from today.

## B6. Search-freshness disqualification rule

**Finding:** Using Eve's own real Session 1 search results (the only session with real, non-stub web-search data on file) with A4's now-fixed `_parse_loose_date`, `tag_lookahead_risk` produces **8 flags (4 distinct sources, each appearing in the search-result block twice)** where the pre-A4 code silently produced **0** — this session's own `lookahead_risk_flags` field, as actually persisted in `docs/site_data/eve_sessions/eve-20260804T020749Z-4cf6e4c9.json`, reads `[]`, which A4's fix would now change to a non-empty list if the session were re-scored. This was a real, silent gap in a session that already counts toward the pre-registered 8 (informational-only, per "flag never discard," so this does not retroactively invalidate Session 1 — but it means Session 1's own real lookahead-risk exposure was never actually surfaced to a human reviewer).

**Confidence:** confirmed-from-data (recomputed directly against the real session file with the fixed parser, real `backtest_window_start` computed from the real PAXG/4h research export: `2024-07-30`, real OOS/test-half start at the project's own `TRAIN_FRACTION=0.7` split: `2025-12-25`).

**Three concrete BINDING rule variants, scored against this real data:**

| Variant | Rule | Flags out of 4 real sources | Verdict on this real sample |
|---|---|---|---|
| A — window-start | `pub_date >= backtest_window_start` (the CURRENT informational logic, made binding) | **4/4** | Disqualifies the session entirely. Too strict as a binding rule: `window_start` is the full history's own earliest point (here, 2 years back) — almost any web source about a still-active market will postdate it. This would make nearly every web-sourced hypothesis on an actively-traded asset unusable. |
| B — OOS/test-half start | `pub_date >= window_start + TRAIN_FRACTION * (window_end - window_start)` (only flag sources describing the held-out test period specifically, the statistically relevant boundary — a source describing the IS/train period is normal domain background, not leakage into the metric that actually decides SURVIVED/DIED) | **4/4** (identical result on this sample — coincidental, not structural: all 4 real sources happen to be within the last 6 months, well inside the ~8-month OOS half of this 2-year window) | Conceptually tighter and more defensible than A (ties the threshold to the actual leakage-relevant boundary, not an arbitrary "since the beginning of time" line) but produces the SAME outcome here, so this one real session cannot distinguish A from B — needs re-evaluation once more real sessions with older/mixed-date sources exist. |
| C — fixed recency window | `pub_date >= session_started_at - 30 days` (flag only "Eve just read something published this week/month" — the single highest-suspicion case: a live recap of very recent price action, independent of where the backtest window sits) | **2/4** (`"3 weeks ago"`, `"1 month ago"` flagged; `"February 1, 2026"`, `"May 20, 2026"` — both real calendar dates, not relative — do not) | The most lenient and the only variant that actually discriminates within this real sample. Catches the specific failure mode most likely to leak real signal (a source describing what the market did in the last few weeks, at exactly the time Eve is choosing entry/exit thresholds) without disqualifying any hypothesis merely for citing an older, more evergreen source (e.g. a 2025 explainer article about how PAXG tracks gold). |

**Recommendation:** Variant C, because it is the only one that isolates the specific mechanism actual lookahead bias would exploit (recent-events leakage) rather than penalizing every web-sourced hypothesis for citing any source published within a multi-year backtest window. Variants A and B both conflate "the source exists somewhere inside a 2-year window" with "the source could plausibly have described what actually happened in the test period" — on an actively-traded asset with a long history, almost every real source fails that test trivially, making the rule uninformative in practice (as this exact sample shows). **This is a recommendation, not a decision already made** — the directive explicitly asked for options with data, not a unilateral implementation, and this is a single real session's worth of evidence; the threshold (30 days) itself is a starting point for the human running the loop to calibrate, not a number derived from a principled bound.

## B7. Multi-timeframe tie-in

**Finding:** `APPROVED_RESEARCH_UNIVERSE` today is `{(BTC,4h), (ETH,4h), (SOL,4h), (PAXG,4h)}` — every entry uses the SAME timeframe. This is a deliberate pre-registration choice, not a structural limitation: `agent_scanner_state.json`'s own `last_regime` map already tracks dozens of `(asset, timeframe)` pairs across MANY timeframes (`1day`, `1week`, `4h`, `24h`, `12h` all appear in the real committed state), and the candle-export infrastructure (`export_candle_data.candle_filename`, the research-export split from A1/5dd51a0) is already keyed by `(asset, timeframe)` generically — nothing in the data layer assumes one timeframe per asset.

**Confidence:** confirmed-from-code (the data layer) / confirmed-from-data (the scanner state's own multi-timeframe tracking) for the "already generic" half; the "deliberate pre-registration choice, not yet expanded" half is confirmed from `asset_universe.py`'s own frozen set contents plus the explicit out-of-scope instruction in this same directive ("do NOT add any new pair... do NOT execute the multi-timeframe rollout").

**Design-question answer (design only, not the rollout):** New timeframes reuse the Factory Loop UNMODIFIED at every stage EXCEPT one: **B4's FDR family boundary must explicitly decide whether a family spans across timeframes for the same asset, or stays scoped per-(asset,timeframe).** Every other stage is already timeframe-generic by construction (Test→Trial, Graveyard distillation, Repair→Trial, provenance tags — none of B1/B2/B3/B5's designs above reference a timeframe anywhere in their own logic). But FDR correction is NOT automatically safe to widen: `benjamini_hochberg`'s guarantee is about the number of independent tests in a family, and BTC/4h and BTC/1d hypotheses testing the SAME underlying mechanism at two timeframes are not independent tests in the way two different assets are (correlated regime state, shared underlying price series) — silently pooling them into one FDR family without accounting for that correlation would understate the true false-discovery risk, the opposite direction this project's own stated discipline ("under-counting is the one direction this must never drift," `budget_ledger.py`'s own words about cost, but the same principle applies to statistical risk) explicitly rules out. **Recommendation for the eventual rollout (not now): keep FDR families scoped per-(asset,timeframe) initially** (the conservative default, matching how `APPROVED_RESEARCH_UNIVERSE` already scopes everything else per-pair) rather than per-asset-across-timeframes, until a specific analysis justifies pooling.

## B8. Public-facing Loop visualization

*Added after the original directive was drafted; findings below are grounded directly in the real `website/` Next.js app, not assumption.*

**Finding — the site's entire data-access architecture is one function, and it has no custom backend.** `website/lib/data.ts`'s `fetchJson<T>(filename)` is the SOLE mechanism every page uses to read live data: it fetches `https://raw.githubusercontent.com/jvmg7nmf6n-hue/project-nero-vatican/main/docs/site_data/{filename}` directly from GitHub's raw-content CDN, with Next.js ISR (`next: { revalidate: 300 }` — a 5-minute cache) and a `try/catch` that returns `null` on any failure rather than throwing ("pages can render an honest fallback instead of crashing when the live data isn't reachable," per the function's own comment). There is no database, no custom API route serving this data (the one existing API route, `app/api/chat/route.ts`, is unrelated — a chatbot endpoint), and no server-side computation beyond `fetch`+`JSON.parse`. Every "live" number on the site today is simply a committed JSON file in `docs/site_data/`, regenerated by a Python-side script or GitHub Actions workflow, and read by the frontend on a 5-minute poll.

**Finding — a real, already-shipped precedent exists for BOTH options in this codebase today, not hypothetically:**
- **Option (a)'s precedent:** `app/methodology/page.tsx` (93 lines) is a pure static page — zero `fetch` calls, zero data dependency, plain prose explaining train/test split, bootstrap CI, random-entry baseline, grid-shift robustness, and the verdict categories (SURVIVED/PROMISING-WATCHLIST/DIED) in plain language, with a link to `/graveyard`. This is the exact shape a Factory Loop explainer should take: same file pattern, same prose register ("plain-language notes on how we decide..."), addable as `app/factory-loop/page.tsx` (or a new section within `/methodology`) with zero new dependencies.
- **Option (b)'s precedent:** `app/lab/page.tsx` already renders LIVE counts today — `ResearchAgentPanel` displays `agent_performance.json`'s cumulative `survived`/`promising_watchlist`/`died`/`untestable` fields (confirmed directly in `components/ResearchAgentPanel.tsx`), fetched via the exact `fetchJson` pattern above. A Factory Loop live-status view is not a new architecture, it is one more `fetchX()` function in `lib/data.ts` plus one more committed JSON file — the same pattern extended, not a new one invented.

**Finding — a real naming collision exists that a Factory Loop page must resolve, not inherit.** `app/lab/page.tsx` already has a section titled **"Repair Workbench"** (`components/RepairWorkbench.tsx`), but it is driven by `repair_candidates.json` — the small, hand-curated file (3 entries, e.g. `RMR_CONFIRMATION_METALS_WEEKLY`) described in B0c/B2 above, NOT by `repair_lab.py`'s real, fully-built-but-unwired chain-record engine (`repair_attempts.json`, per B0b). If B3's "Repair→Trial" pipeline ever ships and also gets called "Repair Workbench" on the public site, there would be two different things with the same public name. **Recommendation: any Factory Loop UI work should either (i) rename the existing hand-curated section (e.g. "Repair Candidates," matching the file's own name) before B3 ships, or (ii) explicitly design the future Repair→Trial UI to replace/absorb the existing section rather than sit alongside it under a duplicate name.**

**Finding — the Factory Loop page would be the FIRST public surface for Eve's work at all.** A precise grep for Eve-specific references (`eve_hypotheses`, `EveSession`, `nero_core.eve`, `Factory Loop`) across `website/app/`, `website/components/`, and `website/lib/` returns zero matches. Only Adam's research agent is currently shown publicly (`ResearchAgentPanel`, sourced from `agent_hypotheses.json`/`agent_test_results.json`/`agent_performance.json`). This is worth stating explicitly because it changes what "ship the static explainer now" actually means: it is not just adding a new page to an existing display, it is the first time this project's own stated transparency principle ("Every signal. Every loss. On the record" — confirmed real copy, `app/layout.tsx` line 7 and `components/HeroStats.tsx`) would extend to Eve's side of the research process at all.

**Finding — no diagramming library exists in the frontend today.** `website/package.json`'s only chart/graphics dependency is `lightweight-charts` (financial candlestick charts). A repo-wide component search for hand-rolled `<svg>` usage found exactly 3 files (`EquityCurveChart.tsx`, `MarketsOverview.tsx`, `Logo.tsx`) — meaning any Loop diagram (boxes/arrows for Adam/Eve → Test → Trial/Graveyard → Repair) needs to be hand-authored SVG/CSS, matching this project's own existing precedent (`Logo.tsx`'s own hand-rolled SVG) rather than pulling in a new diagramming dependency (e.g. Mermaid, React Flow) for what is fundamentally a static 5-6-node flowchart.
