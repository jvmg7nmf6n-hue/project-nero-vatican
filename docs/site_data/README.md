# Manually-Maintained Site Data Files

`site_summary.json`, `graveyard.json`, and `strategy_descriptions.json` in this
directory are **curated by hand**, not regenerated by the live scheduler (contrast
with `ledger_full.json`, `ledger_recent.json`, `stats.json`, `strategies.json`, which
`nero_core/execution/export_site_data.py` overwrites every run). Update these three
only when a new research batch completes and changes the picture, or a new strategy
family is added — never auto-scrape or auto-generate them.

`strategy_descriptions.json` is a flat `{ strategy_id: "plain-language mechanism
description" }` map, keyed by strategy_id (the family name, e.g. `"PEAD"`) — ONE
description per family, not per individual config/version/asset, since the mechanism
is the same regardless of which asset it's wired to. Consumed by
`website/app/strategy/[id]/page.tsx`'s "what this strategy does" header; a family with
no entry here falls back to a generic "hasn't been added yet" message on the site
rather than a broken page.

`strategies.json`'s `source_report` field (added for Step 4, individual strategy
pages) is populated by `nero_core/execution/source_reports.py`, which mirrors
`verification_status.py`'s exact (strategy_id, strategy_version, asset) key
discipline and the same reasoning: RANGE_MEAN_REVERSION wires two different versions
against the same asset (BTC), so keying on (strategy_id, asset) alone would let one
config's status leak onto the other. A config with no historical backtest at all
(NEWS_SENTIMENT, ORDERFLOW_IMBALANCE) maps to `null`, never a fabricated path.

`heartbeat.json` is a third category: written automatically by
`nero_core/execution/heartbeat.py` after every successful live-scheduler run (see
`nero_core/execution/live_scheduler.py::main`) — never hand-edit it, the same way you
wouldn't hand-edit `stats.json`. It exists purely as a dead-man's-switch signal for
`nero_core/execution/scheduler_heartbeat_alert.py` and the `Scheduler Heartbeat Check`
GitHub Actions workflow, and optionally for the website's small "system status"
indicator (`website/lib/systemStatus.ts`).

## `site_summary.json` — how the numbers were derived (as of 2026-07-25)

**Recount history:** the 2026-07-18 version of this file counted `configs_tested: 67`
and `strategies_survived: 1` from a small early subset of research reports. A week of
additional research batches (Donchian cross-asset, metals/stocks/forex full sweeps,
PSX, RANGE_MEAN_REVERSION + its ranging-regime and variant-research follow-ons, PEAD,
GOLD_SILVER_RATIO_MR, CARRY_MOMENTUM, MACRO_RISK_ON, trail-exit and filter A/Bs, the
vol-clustering comparative) made that number badly stale — the live roster alone grew
to 17 verified configs while `site_summary.json` still said 1, an internal
contradiction a site visitor could catch immediately. This section documents the full
recount across every `docs/*.md` report that exists as of this date, so the numbers
stop drifting silently.

**`configs_tested: 1515`** — the count of distinct (asset/pair, timeframe, strategy_id
+ version) combinations that were actually backtested with real reported trade counts
and expectancy, across every completed research report in `docs/*.md`, with these
rules:

1. **Deduplicated across docs.** The same exact config (same asset/pair, timeframe,
   strategy_id, and version) re-tested in a later report — as a reference baseline, a
   robustness re-check, a bootstrap-CI re-verification, or a multiplier ON/OFF
   comparison — counts ONCE, credited to whichever doc reports its first real
   backtest with reported trade counts. A **new registered version** (this project
   never mutates a live strategy's parameters in place — see `nero_core/strategies/
   registry.py`) DOES count as an additional config, since it is a distinct, separately
   evaluated variant.
2. **Excludes data-audit-only investigations** where no strategy was ever backtested —
   any `*_data_audit.md`, `*_calibration_audit.md`, or `*_data_pipeline.md` report,
   plus `etf_flow_audit.md`, `white_house_audit.md`, `liquidation_predictor_data_audit.md`,
   and `psx_task3_pead_gate.md` (all gate/feasibility checks, zero strategy runs).
   `nero_analysis.md` and `phase0_1_summary.md` are scaffold/analysis docs, not
   strategy reports.
3. **Excludes pure closing/consolidated reports** that only cite and sum numbers
   already reported in their own sibling primary-sweep docs (e.g.
   `donchian_deep_dive_closing_report.md` cites Task 2's 37; `ranging_regime_batch_
   closing_report.md` cites R1+R2+R3's 14+7+2) — counting both the summary and the
   primary doc would double the number.

**`strategies_survived: 17`** and **`strategy_families_verified: 4`** — as of this
date, `docs/site_data/strategies.json` carries 17 roster entries whose
`verification_status` starts with `verified` or `triple-verified` (see
`website/lib/tier.ts::classifyTier` for the exact classification the live site uses —
the website computes this number directly from the live roster rather than reading it
from this file, so it can never drift out of sync the way the old `1` did). Of those
17, **14 are PEAD** (7 tickers x 2 alert thresholds, one signal family), and the
remaining 3 are one config each of BREAKOUT_MOMENTUM, TREND_PULLBACK, and
COINTEGRATION_PAIRS — **4 distinct verified strategy families total**. Reporting only
"17 verified" without the family breakdown would be technically true but easy to
misread as "17 different strategies," which is why both numbers are tracked here and
both are shown on the site. This is a looser bar than the old `strategies_survived: 1`
column, which used the strictest possible SURVIVED classification (positive
expectancy AND adequate sample AND CI clears zero on both halves, grid-shift included
where applicable) rather than the site roster's three-tier verified/watchlist/
experimental grouping — the two numbers answer different questions (rigorous
backtest-verdict vs. live-roster display tier) and are not directly comparable.

Not counted anywhere in `configs_tested` (no dedicated `docs/*.md` report exists for
their own standalone numbers, even though they exist in the codebase/git history):
SHORT_MOMENTUM, DONCHIAN_TREND (the v1 long-only trailing-exit strategy — distinct
from `DONCHIAN_TREND` v2.0.0-bracket, which IS counted via `donchian_task2_full_sweep.md`),
the volume-confirmed BREAKOUT_MOMENTUM variant. If a report for these is ever written,
add their configs here.

## `graveyard.json` — sourcing

One entry per distinct killed strategy/config-family, each `source_doc` pointing at
the actual completed report the "why it died" summary is drawn from. Authored once
from the reports existing as of 2026-07-18 — update this file (add entries, don't
rewrite existing ones) after future research batches complete, rather than
auto-scraping `docs/*.md`, since "why it died" is a synthesized judgment call a script
shouldn't be trusted to make unsupervised.
